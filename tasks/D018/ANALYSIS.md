## 1. カバレッジ目標の現状と根拠

### 1.1 現行のカバレッジ目標

**SPEC.md § 9.1:**
```
バックエンド:
├─ Service層:   ≥ 80%（最重要）
├─ Views:       ≥ 60%
├─ Models:      ≥ 70%（複雑なメソッドのみ）
└─ Utils:       ≥ 80%

フロントエンド:
├─ Services/Hooks: ≥ 70%
├─ Components:     ≥ 50%（重要なもののみ）
└─ Utils:          ≥ 80%
```

**CLAUDE.md（簡略版）:**
```
- Service層: カバレッジ≥80%
- Views: カバレッジ≥60%
- Hooks: カバレッジ≥70%
```

### 1.2 根拠の有無

**結論: 明示的な根拠は記載されていない**

SPEC.md・CLAUDE.mdのいずれにも、これらの数値がなぜ選ばれたかの説明はない。
以下は推測される根拠:

| 層 | 目標 | 推測される理由 |
|----|------|--------------|
| Service層 80% | 高 | ビジネスロジックが集中、バグのリスクが高い |
| Views 60% | 中 | HTTP処理のみ、ロジックは薄い設計 |
| Models 70% | 中 | 複雑なメソッドのみ対象、プロパティは除外 |
| Hooks 70% | 高 | 状態管理ロジックが集中 |
| Components 50% | 低 | UIのみ、ロジックはhooksに分離 |
| Utils 80% | 高 | 共通処理、複数箇所で使用 |

### 1.3 業界標準との比較

一般的なカバレッジ目標の参考値:

| 層 | 業界目安 | 本プロジェクト | 評価 |
|----|---------|--------------|------|
| ビジネスロジック | 80-90% | 80% | 適切 |
| Controller/View | 50-70% | 60% | 適切 |
| UI Components | 30-50% | 50% | 適切 |
| 共通ユーティリティ | 80-100% | 80% | 適切 |

**所見:** 数値自体は業界標準に合致しており妥当。ただし根拠を明文化すべき。

### 2.3 不足している観点

1. **境界値テスト**
   - パスワード長の最小値・最大値
   - メールアドレスの最大長
   - display_nameの最大長（100文字）
   - 半径検索のMAX_RADIUS_KM境界

2. **同時実行・競合状態**
   - 同時ログイン
   - トークンリフレッシュの競合

3. **セキュリティテスト**
   - SQLインジェクション耐性
   - XSS耐性
   - CSRF保護

4. **パフォーマンステスト**
   - 大量データでの検索速度
   - 同時接続数

## 3. テストの種類と現状

### 3.1 テスト種別の定義と実装状況

| テスト種別 | 定義 | SPEC記載 | 実装状況 |
|-----------|------|---------|---------|
| 単体テスト | 関数・クラス単位 | ✅ あり | ✅ 実装あり |
| 結合テスト | モジュール間連携 | ✅ あり（§9.4） | ⚠️ 一部 |
| E2Eテスト | UI〜DB全体 | ❌ なし | ❌ なし |
| シナリオテスト | ユースケース全体 | ❌ なし | ❌ なし |
| リグレッションテスト | 既存機能の維持 | ❌ なし | ⚠️ CI上で間接的に |
| 境界値テスト | 入力の限界値 | ❌ なし | ❌ なし |
| セキュリティテスト | 脆弱性検出 | ❌ なし | ❌ なし |
| パフォーマンステスト | 速度・負荷 | ❌ なし | ❌ なし |

### 3.2 現行で実施されているテスト

**バックエンド:**
- pytest + pytest-django
- DRF APIClient での統合テスト
- Fixtureベースのテストデータ

**フロントエンド:**
- Vitest + React Testing Library
- TanStack Query の renderHook
- vi.mock でのモック

### 3.3 不足しているテスト種別

| 種別 | 優先度 | 理由 |
|------|--------|------|
| E2Eテスト | 高 | ユーザー視点での動作保証が必要 |
| 境界値テスト | 高 | バリデーションエラーの品質担保 |
| セキュリティテスト | 高 | OAuth、JWT周りの脆弱性 |
| シナリオテスト | 中 | 主要ユースケースの検証 |
| パフォーマンステスト | 低 | MVP後で可 |

### 9.5 テストケース分類

各テストは以下のカテゴリを明示すること:

- **正常系 (Happy Path):** 期待通りの入力での動作
- **異常系 (Error Cases):** エラー時の動作
- **境界値 (Boundary):** 入力の限界値での動作
- **状態遷移:** loading/success/error状態の遷移

### 9.6 境界値テスト例

```python
@pytest.mark.parametrize("radius_km,expected", [
    (0.1, True),     # 最小有効値
    (100, True),     # 最大有効値
    (100.1, False),  # 最大超過
    (0, False),      # ゼロ
    (-1, False),     # 負数
])
def test_radius_boundary(radius_km, expected):
    ...
```
```

## 7. 結論

### 7.1 現状評価

- **カバレッジ目標:** 適切だが根拠が未記載
- **テスト種別:** 単体・結合は実装済み、E2E・境界値・セキュリティは未整備
- **ドキュメント:** SPEC.mdとCLAUDE.mdの一部不一致あり

### 7.2 優先度の高い改善

1. **SPEC.md § 9.1.1 追加:** カバレッジ目標の根拠を明文化
2. **境界値テストガイドライン:** 特に地理計算（半径検索）で重要
3. **セキュリティテスト方針:** OAuth/JWT周りの脆弱性対策

### 7.3 qa-test-engineerへの提言

- 実装タスク完了時には**必ず境界値テストケースを抽出**する
- エラーメッセージの期待値を明確化し、テストで検証する
- SPEC.mdに記載のない仕様ギャップを発見した場合は報告する
